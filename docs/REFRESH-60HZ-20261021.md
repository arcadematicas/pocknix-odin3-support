# Cambio de refresco del panel (60/120 Hz) en AYN Odin 3 — investigación cross-proyecto

Fecha: 2026-10-21
Autor: agente de investigación (solo lectura, no se ha modificado el proyecto)
Contexto: kernel mainline 7.2.11 + parches ROCKNIX/armada. Panel Chipone ICNA3520
AMOLED 1080x1920, driver `panel-chipone-icna35xx` con el parche ROCKNIX
`0518-ROCKNIX-odin3-panel-frame-length-calibration.patch` (sysfs `frame_len_60/120`).

---

## 1. Resumen ejecutivo

**Sí existe una "solución de referencia", pero no es un parche puntual: es una
arquitectura.** Dos proyectos mantienen el mismo panel ICNA3520 en la Odin 3 con
60/120 Hz funcional, y **ninguno de los dos deja que kwin (KDE/Plasma) toque el
conector DRM directamente**:

- **armada-os/armada**: el panel lo posee SIEMPRE `gamescope` (es el *DRM master*).
  Plasma/kwin corre *anidado* dentro de gamescope (`DISABLE_GAMESCOPE_WSI=1`,
  unidades `armada-plasma-nested-*`). El cambio de refresco lo hace Steam
  (menú QAM) → protocolo `gamescope_control.set_app_target_refresh_cycle` →
  `drm_set_mode()`.
- **ROCKNIX**: usa **Sway + EmulationStation** (no gamescope, no kwin). El cambio de
  modo se hace con `wlr-randr`/`set_refresh_rate`, y funciona (su script de
  calibración cambia 60↔120 explícitamente).

El fallo que tenéis (`kscreen-doctor output.DSI-1.mode.2` → `dsi_cmds2buf_tx ... ret=-110`
en el primer comando de la init + `Skipping unprepare of already unprepared panel`)
**no aparece documentado en ningún issue/PR de armada ni de ROCKNIX**, porque en esas
distros el camino que lo dispara (kwin como dueño del conector DSI) no se usa para el
panel principal. Es decir: **no hay un fix kwin-específico conocido**.

Puntos clave que sí están documentados y que afectan directamente a vuestro caso:

1. ROCKNIX ya fusionó **PR #2884 "sm8750: fix panel initialization in gamescope"**
   (junio 2026): añade `enabled` flag, re-aplica el backlight en la init, y —lo más
   importante— **salta la escritura de brillo mientras el panel está apagado** para no
   "atascar el motor de comandos DSI" tras un modeset. Vosotros ya tenéis este fix
   (vuestro `0028` es idéntico al post-#2884).
2. ROCKNIX **PR #3484 "RP6/Odin 3: add display refresh rate calibration"** (fusionado
   2026-10-10) **es exactamente vuestro parche 0518** (mismo commit
   `3c45806c8f52...`). Su script `rocknix-panel-calibration` **cambia el modo 60↔120
   con `wlr-randr`** para calibrar cada tasa.
3. armada lleva **dos parches DSI adicionales que vosotros NO tenéis**: `0048a`
   (redondeo del byte clock tras reparentar al PLL, de Qualcomm upstream) y `0048b`
   (init del bias PLL en PHY 7nm). Aunque el pixel clock de 60 y 120 Hz es casi
   idéntico (ver §4), el re-power-cycle del host DSI que dispara un cambio de modo
   pasa por exactamente ese código.

Conclusión: **la causa más probable no es el driver del panel (que re-inicia bien),
sino la secuencia disable/enable que kwin genera sobre el host DSI msm**; el camino
que funciona en producción es el de gamescope/Sway. La recomendación de menor coste
es no dejar que kwin cambie el modo del panel (arquitectura tipo armada), y de forma
independiente portar `0048a`/`0048b`.

## 2. Qué hace cada proyecto (rutas exactas y código)

### 2.1 armada-os/armada (rama principal, HEAD `d2bcf6fd`)

#### 2.1.1 Driver de panel — selección de modo por modo DRM activo

`packages/kernel/patches/0028-drm-panel-Add-panel-driver-for-Chipone-ICNA35XX-base.patch`

El driver (de Teguh Sobirin, base de ROCKNIX y armada) **NO usa sysfs de calibración**.
Elige la longitud de trama leyendo el modo DRM actual en cada `prepare()`:

```c
static int icna35xx_get_current_mode(struct panel_info *pinfo)
{
	struct drm_connector *connector = pinfo->connector;
	struct drm_crtc_state *crtc_state;
	int i;
	if (!connector->state || !connector->state->crtc)
		return 0;                          /* modo por defecto */
	crtc_state = connector->state->crtc->state;
	for (i = 0; i < pinfo->desc->num_modes; i++)
		if (drm_mode_match(&crtc_state->mode, &pinfo->desc->modes[i],
				   DRM_MODE_MATCH_TIMINGS | DRM_MODE_MATCH_CLOCK))
			return i;
	return 0;
}
```

Y en `icna3520_init_sequence()` la longitud de trama va **hardcodeada** según el
refresco (120 → `0x4C`, 60 → `0x7D6`):

```c
	if (cur_vrefresh == 120) {
		mipi_dsi_generic_write_seq_multi(&dsi_ctx, 0x48, 0x00);
		mipi_dsi_generic_write_seq_multi(&dsi_ctx, 0x9F, 0x00);
		mipi_dsi_generic_write_seq_multi(&dsi_ctx, 0xB3,
                0x00, 0xD8, 0x00, 0x1C, 0x00, 0x4C);
	} else {
		mipi_dsi_generic_write_seq_multi(&dsi_ctx, 0x48, 0x10);
		mipi_dsi_generic_write_seq_multi(&dsi_ctx, 0x9F, 0x00);
		mipi_dsi_generic_write_seq_multi(&dsi_ctx, 0xB3,
                0x00, 0xDB, 0x00, 0x1C, 0x00, 0x1C, 0x00, 0x00,
				0xDB, 0x00, 0x1C, 0x07, 0xD6, 0x00);   /* 0x7D6 = 2006 */
	}
```

Los dos modos DRM (`icna3520_modes[]`) son los mismos que tenéis: 120 Hz (vfp 28,
vtotal 1977) y 60 Hz (vfp 2006, vtotal 3955). El `prepare()` hace el ciclo completo
cada vez (reset + init), así que **un cambio de modo re-ejecuta la init con la trama
correcta**:

```c
static int icna35xx_prepare(struct drm_panel *panel)
{
	...
	ret = regulator_bulk_enable(ARRAY_SIZE(panel_supplies), pinfo->supplies);
	...
	icna35xx_reset(pinfo);            /* pulso de reset del panel */
	ret = pinfo->desc->init_sequence(pinfo);   /* re-envía 0x9C A5 A5 ... */
	...
}
```

> Nota: el primer comando de la init (`0x9C 0xA5 0xA5`) es idéntico al vuestro. Si a
> armada le funciona el cambio de modo y a vosotros no, la diferencia **no está** en
> esta secuencia sino en *quién* y *cómo* dispara el modeset.

#### 2.1.2 Perfil de display edidless (Lua) — el refresco viene del kernel

`system_files/usr/share/gamescope/scripts/10-armada/ayn.icna3520.oled.lua`

```lua
-- ICNA3520 OLED used by the AYN Odin 3 ...
-- ... Refresh rates come from the kernel mode list. Steam owns HDR behavior at runtime.
gamescope.config.known_displays.armada_ayn_icna3520_oled = {
    pretty_name = "AYN ICNA3520 internal OLED",
    colorimetry = { r={x=0.6800,y=0.3200}, ... },
    hdr = { supported=true, eotf=gamescope.eotf.gamma22, max_content_light_level=650, ... },
    matches = function(display)
        if (display.device_id == "ayn-odin-3" or display.device_id == "ayn-thor")
            and display.internal and not display.has_edid then
            return 6000
        end
        return -1
    end,
}
```

El perfil **solo** aporta colorimetría/HDR. No define `dynamic_refresh_rates`: gamescope
obtiene [60, 120] directamente de la lista de modos del kernel (ver §2.4). El comentario
"Refresh rates come from the kernel mode list. Steam owns ... at runtime" confirma que el
cambio de refresco es responsabilidad de Steam/gamescope, no del driver.

#### 2.1.3 Quirks de refresco por dispositivo (gamescope-session-plus)

`packages/gamescope-session/patches/0009-fix-konkr-fit-refresh-rates.patch` (y 0007/0008):

```sh
if [[ ":KONKR Pocket FIT:" =~ ":$SYS_ID:" ]]; then
  ORIENTATION=right
  CUSTOM_REFRESH_RATES=60,90,120,144
  OUTPUT_CONNECTOR='*,DSI-1'
  FAKE_OUTPUT_MM=177x100
  export STEAM_DISPLAY_REFRESH_LIMITS=60,90,120,144
fi
```

- `CUSTOM_REFRESH_RATES` → argumento `--custom-refresh-rates` del fork gamescope de
  OpenGamingCollective (gamescope 3.16.x-ogc): filtra/exhibe las tasas permitidas.
- `STEAM_DISPLAY_REFRESH_LIMITS` → dice a Steam qué tasas mostrar en QAM.

Para la **Odin 3 no hay entry** en `device-quirks`: se fía de la lista del kernel
(60 y 120). El dispositivo solo define orientación y nits:
`system_files/usr/lib/armada/devices/ayn-odin-3.conf` →
`ARMADA_DEVICE_ID=ayn-odin-3`, `ARMADA_SOC_CLASS=SM8750`, `ARMADA_PANEL_ORIENTATION=right`,
`ARMADA_HDR_NITS=650`.

#### 2.1.4 Plasma/kwin SIEMPRE anidado en gamescope (la clave)

`system_files/usr/libexec/armada/armada-plasma-session`:

```sh
nested_unit_glob='armada-plasma-nested-*.service'
...
export DISABLE_GAMESCOPE_WSI=1
...
[[ -n "${DISPLAY:-}" ]] || fail "nested Gamescope did not provide an X11 display"
```

`system_files/usr/libexec/armada/bottom-gamescope` lanza gamescope como DRM master:

```sh
exec "$gamescope" --backend drm --drm-lease-client "$lease_socket" --drm-lease-yield \
    --expose-wayland --force-windows-fullscreen --xwayland-count 1 ...
```

Es decir: **en armada, kwin jamás es dueño de `DSI-1`**. Por eso `kscreen-doctor
output.DSI-1.mode.2` no existe como camino de producción y no hay bug de cambio de
modo vía kwin.

#### 2.1.5 Parches DSI que armada tiene y vosotros no

`packages/kernel/patches/series` (líneas 8–10):

- `0048-drm-msm-dsi-reparent-byte-pixel-src-to-xo-on-disable.patch` (tenéis este)
- `0048a-drm-msm-dsi-round-byte-clock-rate-after-reparenting-to-PLL.patch` (**NO lo tenéis**)
- `0048b-drm-msm-dsi-fix-pll-init-in-bonded-mode.patch` (**NO lo tenéis**)

`0048a` (Dmitry Baryshkov, Qualcomm, patchwork 750496) mueve el `clk_round_rate` del
byte clock a `dsi_link_clk_set_rate_6g()` (después de reparentar el RCG al PLL), porque
en hosts DSI 6G v2.9 (SM8650/**SM8750**) el redondeo se hacía antes de reparentar y el
PLL podía programarse a frecuencia errónea "breaking the panel". `0048b` (virtudude)
inicializa `PLL_SYSTEM_MUXES` y deja asentar el bias al habilitar el PHY 7nm.

#### 2.1.6 Issue conocido relevante

- armada #589 / #590 (abierto): *"Odin 3 Gamescope FPS limiter consistently
  undershoots target by ~1 FPS (30→29, 40→39, 60→59)"*. Coincide con vuestra medida de
  **120,04 Hz**: el modo "120 Hz" del panel oscila en ~120,04 Hz por unidad (ver §4),
  que es justo lo que corrige la calibración de `frame_len`.

### 2.2 ROCKNIX/distribution (rama `next`; clone local en `18aded5898`)

> Importante: vuestro parche **0518 no es "algo propio sobre ROCKNIX": es literalmente
> el ROCKNIX PR #3484** (mismo `From 3c45806c8f520ec746c80d7652496f30599e4738`), fusionado
> en `next` el 2026-10-10. El clone local es anterior a ese merge, por eso no lo veíais.

#### 2.2.1 PR #2884 — "sm8750: fix panel initialization in gamescope" (junio 2026)

Commit `b59f018e09` / merge `1f44f7e9c2`. Aporta al driver base `0028`:

- campos `backlight` y `enabled` en `panel_info`;
- callback `enable()` que marca `pinfo->enabled = true`, y `enabled = false` en `disable()`;
- **re-aplica el brillo en la init** (`0x51` antes de `set_display_on`);
- **salta la escritura de brillo si el panel está apagado** (comentario literal):

```c
	/*
	 * Only drive the DSI link while the panel is enabled and streaming.
	 * A brightness write that races panel bring-up or the first frame
	 * kickoff after a modeset wedges the DSI command engine. The level
	 * is cached by the backlight core and re-applied from init_sequence()
	 * on every prepare(), so skipping the write while disabled is safe.
	 */
	if (!pinfo->enabled)
		return 0;
```

- `pinfo->panel.prepare_prev_first = true;` (el `prepare()` del panel ocurre antes que
  el elemento previo del bridge).
- y añade el parche DSI `0048` (reparent a XO) que ya tenéis.

Este commit describe **exactamente** vuestro síntoma: una escritura de brillo que
"wedges the DSI command engine" tras un modeset produce exactamente el
`dsi_cmds2buf_tx ... cmd dma tx failed ... ret=-110`. Vosotros ya tenéis el fix
(vuestro `0028` tiene `pinfo->enabled`, el salto de brillo y `prepare_prev_first`).

#### 2.2.2 PR #3484 — calibración de refresco (= vuestro 0518)

Ficheros del PR:

- `projects/ROCKNIX/devices/SM8750/patches/linux/0518-ROCKNIX-odin3-panel-frame-length-calibration.patch`
- `projects/ROCKNIX/devices/SM8550/patches/linux/0508-ROCKNIX-rp6-panel-frame-length-calibration.patch` (RP6)
- `projects/ROCKNIX/packages/rocknix/sources/scripts/rocknix-panel-calibration`
- `projects/ROCKNIX/packages/hardware/quirks/devices/AYN Odin 3/040-panel_calibration`
- `projects/ROCKNIX/packages/hardware/quirks/profile.d/999-export` (exporta `DEVICE_PANEL_CALIBRATION`)

El cuerpo del PR explica el mecanismo de fondo (clave para entender por qué calibra y
por qué "60 no converge" en vuestro caso):

> "Both panels set their refresh rate from their own oscillator, which varies from unit
> to unit. An RP6 here ran at 60.565 Hz and 121.103 Hz instead of 60 and 120 ... Android
> corrects this per unit through the vendor DSI driver's quec-refresh nodes, using a
> value FactoryTest.apk stores in /mnt/vendor/persist/odin/fps."
>
> "Panel drivers: expose the 120/60 Hz frame length as frame_len_120 and frame_len_60 in
> sysfs. A write applies immediately, the same command the vendor driver resends ..."

La aplicación en vivo de `frame_len` (que es lo que usa la calibración) está en
`icna3520_frame_len_store()`: si el panel está habilitado **y** `vrefresh` coincide,
escribe la trama y re-emite `0x9F 0x0D`. Idéntico a vuestro `0518`.

El script de calibración de ROCKNIX **cambia de modo con Sway** (esto es lo que a
vosotros os falta):

```bash
# rocknix-panel-calibration (fragmento)
PANEL=$(dirname /sys/bus/mipi-dsi/devices/*/frame_len_60)
OUTPUT=$(wlr-randr | awk 'NR==1 {print $1}')
CURRENT=$(wlr-randr --output ${OUTPUT} | awk '/current/ {print $3}')

for RATE in 60 120; do
  MODE=$(wlr-randr --output ${OUTPUT} | awk -v r=${RATE} '/ px, / && int($3 + 0.5) == r {print $3}')
  echo "Calibrating ${RATE} Hz..."
  set_refresh_rate ${MODE}      # <-- cambia el modo DRM real (wlroots)
  sleep 2
  VALUE=$(calibrate ${PANEL}/frame_len_${RATE} ${RATE}) || break
  set_setting display.frame_len_${RATE} ${VALUE}
done
set_refresh_rate ${CURRENT}
```

El *quirk* de arranque aplica los valores guardados:

```sh
# 040-panel_calibration
PANEL=$(dirname /sys/bus/mipi-dsi/devices/*/frame_len_120)
for RATE in 120 60; do
  VALUE=$(get_setting display.frame_len_${RATE})
  [ -n "${VALUE}" ] && echo ${VALUE} >${PANEL}/frame_len_${RATE}
done
```

La wiki de ROCKNIX confirma que la Odin 3 usa **Sway + Emulation Station** (no
gamescope, no kwin). Es decir: **el cambio de modo que funciona en ROCKNIX es el de
wlroots (`wlr-randr`)**.

#### 2.2.3 Comparación `icna3520_set_frame_len` (ROCKNIX 0518) vs vuestro

Son **idénticos**. Vuestro `0518` y el ROCKNIX #3484 tienen el mismo `From` y el mismo

### 2.3 Batocera / ChimeraOS / Bazzite

- **Batocera**: no hay soporte SM8750 / Odin 3 ni driver `icna35xx` (Batocera es
  mayoritariamente x86 y ARM antiguo). Sin hallazgos.
- **ChimeraOS / Bazzite**: heredan `gamescope-session-plus` de OpenGamingCollective.
  El mecanismo de refresco es el mismo que armada: `device-quirks` con
  `CUSTOM_REFRESH_RATES` + `STEAM_DISPLAY_REFRESH_LIMITS`. No hay nada específico de
  Odin 3 / ICNA3520. El fork gamescope `-ogc` (OpenGamingCollective) es el que añade
  `--custom-refresh-rates` (no existe en gamescope upstream, ver §2.4).

### 2.4 gamescope upstream (ValveSoftware/gamescope, HEAD `aa289ea`, 2026-10-20)

#### 2.4.1 `-r` NO fuerza el modo DRM (es el limitador anidado)

`src/main.cpp`:

```c
{ "nested-refresh", required_argument, nullptr, 'r' },
...
"  -r, --nested-refresh           game refresh rate (frames per second)\n"
...
g_nNestedRefresh = gamescope::ConvertHztomHz( parse_integer( optarg, "nested-refresh" ) );
```

`g_nNestedRefresh` es el *limiter* usado cuando gamescope corre anidado. En el backend
DRM sí se pasa a `init_drm()` como `preferred_refresh` y puede influir en la selección
inicial (`find_mode(...)`), pero **su función principal es limitar fps, no cambiar el
modo**. Esto confirma vuestro síntoma #3 ("`-r 60` solo limita fps").

#### 2.4.2 El interruptor de refresco real es el protocolo `gamescope_control`

`protocol/gamescope-control.xml`:

```xml
<event name="active_display_info" since="2">
  ...
  <arg name="valid_refresh_rates" type="array" summary="... 32-bit unsigned integers."/>
</event>
<request name="set_app_target_refresh_cycle" since="2">
  <arg name="fps" type="uint" .../>
  <arg name="flags" type="uint" enum="target_refresh_cycle_flag" .../>
</request>
<!-- flags: internal_display=0x1, allow_refresh_switching=0x2, only_change_refresh_rate=0x4 -->
```

Servidor (`src/wlserver.cpp:1283`) → `steamcompmgr_set_app_refresh_cycle_override()` →
`_update_app_target_refresh_cycle()` (`src/steamcompmgr.cpp:1226`) → calcula
`g_nDynamicRefreshRate` → `HackTemporarySetDynamicRefresh()` →
`drm_set_mode()` (`src/Backends/DRMBackend.cpp:3729`), que **sí hace el modeset real**
(disable/enable del panel → re-init con la trama del modo elegido).

`gamescopectl` (`src/Apps/gamescopectl.cpp`) **solo imprime** `ValidRefreshRates`; no
hay comando para cambiarlo. El cliente que lo pide es Steam (u otro cliente del
protocolo). Esto confirma vuestro síntoma #3 ("gamescopectl reporta ValidRefreshRates:
60, 120 pero no hay comando").

#### 2.4.3 No existe `--custom-refresh-rates` en upstream

El listado de opciones de `src/main.cpp` no contiene `custom-refresh-rates` ni
`g_customRefreshRates` (este símbolo solo aparece como `extern` en los parches de armada
0011/0013/0016, es decir, pertenece al fork `-ogc`). En upstream actual, las tasas
válidas se obtienen de la lista de modos del kernel:

`src/Backends/DRMBackend.cpp:2728`:

```c
// Unknown display ... build ValidDynamicRefreshRates from kernel modes
for (int i = 0; i < m_pConnector->count_modes; i++) {
	const drmModeModeInfo *pMode = &m_pConnector->modes[i];
	if (pMode->hdisplay != pPreferredMode->hdisplay || pMode->vdisplay != pPreferredMode->vdisplay)
		continue;
	if ( !Algorithm::Contains( m_Mutable.ValidDynamicRefreshRates, pMode->vrefresh ) )
		m_Mutable.ValidDynamicRefreshRates.push_back( pMode->vrefresh );
}
```

Para un display "conocido" por Lua se puede además definir `dynamic_refresh_rates` +
`dynamic_modegen` (generador de modos) — armada no lo usa para la Odin 3.

## 3. Recomendación concreta (ordenada por coste/riesgo)

### R1 (coste bajo, impacto alto): sacar a kwin del camino del panel

Reproducid la arquitectura de armada o de ROCKNIX; **no** intentéis arreglar kwin
primero.

- Opción A (armada): gamescope como DRM master SIEMPRE; Plasma/kwin anidado
  (`DISABLE_GAMESCOPE_WSI=1`). El cambio de refresco pasa por Steam QAM /
  `gamescope_control`.
- Opción B (ROCKNIX, la más simple de validar): desktop con Sway; cambio de modo con
  `wlr-randr --output DSI-1 --mode <modo60>`.

Validación inmediata en el hardware (sin tocar nada): arrancad Sway o gamescope como
dueño del conector y haced el cambio 120→60. Si **funciona**, el driver del panel está
bien y el bug es 100% del modeset de kwin. Si **falla igual**, el problema está en el
host DSI (pasad a R2).

### R2 (coste bajo, kernel): portar los parches DSI que faltan

Portad desde armada:

- `0048a-drm-msm-dsi-round-byte-clock-rate-after-reparenting-to-PLL.patch` (Qualcomm,
  con `Tested-by`; corrige el byte clock del PLL en hosts 6G v2.9 = SM8750).
- `0048b-drm-msm-dsi-fix-pll-init-in-bonded-mode.patch` (init de `PLL_SYSTEM_MUXES` +
  settle en PHY 7nm).

Aunque el pixel clock de 60 y 120 Hz es casi idéntico (§4), un cambio de modo fuerza un
power-cycle del host DSI que pasa por este código. Riesgo bajo (uno es upstream
Qualcomm), y es la única diferencia de kernel relevante entre armada (que sí rota
modos) y vosotros.

### R3 (coste bajo/medio): 60 Hz como *preferred* si queréis arrancar en 60

En el driver, `get_modes()` marca el primer modo como `DRM_MODE_TYPE_PREFERRED`:

```c
mode->type = DRM_MODE_TYPE_DRIVER;
if (i == 0)
	mode->type |= DRM_MODE_TYPE_PREFERRED;
```

Para que el sistema arranque en 60 Hz por defecto, poned el modo 60 primero (o
intercambiad el orden en `icna3520_modes[]` / marcádselo en el DTS). Ojo: gamescope
tiene "refresh doubling" (`_update_app_target_refresh_cycle` elige el mayor múltiplo:
para un objetivo de 60 fps elige 120), así que esto solo fija el modo de arranque, no
el comportamiento en juego.

### R4 (coste medio): arreglar el QAM de Steam ARM64

Si el QAM "muestra la frecuencia pero no la aplica", el cliente no está enviando (o
gamescope no está procesando) `set_app_target_refresh_cycle`. Verificar:

1. ¿gamescope es el DRM master? (si kwin es el dueño, Steam no puede cambiar el modo).
2. ¿`gamescopectl` (o un mini-cliente del protocolo) puede pedir el cambio? Probad un
   cliente de prueba que envíe `set_app_target_refresh_cycle(60, INTERNAL|ALLOW_SWITCH|ONLY_CHANGE_REFRESH)`.
3. ¿El fork gamescope que usáis expone `--custom-refresh-rates` / `CUSTOM_REFRESH_RATES`
   (fork `-ogc`) y `STEAM_DISPLAY_REFRESH_LIMITS` está exportado a Steam?

### R5 (coste alto, último): corregir kwin (si de verdad lo necesitáis)

Solo si R1/R2 no bastan y queréis kwin como dueño directo. El síntoma
(`Skipping unprepare of already unprepared panel` → primer comando de init con `-110`)
apunta a que kwin **no hace un ciclo disable→unprepare→prepare→enable correcto** (o lo
hace sin respetar `prepare_prev_first`, o deja el host DSI sin reloj al reintentar).
Esto es trabajo en el backend DRM/KMS de kwin (o en `drm_panel.c` del kernel), sin
solución conocida publicada. Ver §4 para el experimento discriminador.

## 4. Diagnóstico y experimento discriminador (si no hay solución kwin conocida)

**No hay solución kwin-específica publicada.** Antes de invertir en kwin, discriminad la
causa con estos pasos (en el hardware, sin modificar el proyecto):

1. **Cálculo de clocks (dato previo):** los dos modos tienen casi el mismo pixel clock
   (porque 60 Hz se hace con un VFP enorme):
   - 120 Hz: htotal 1129 × vtotal 1977 → ≈267,84 MHz
   - 60 Hz:  htotal 1129 × vtotal 3955 → ≈267,91 MHz
   ⇒ el cambio 60↔120 **apenas re-negocia el PLL/byte clock**. El fallo no debería ser
   de frecuencia de reloj, sino del **estado del motor de comandos DSI / secuencia de
   power del panel**.

2. **Experimento A — ¿es la carrera disable/enable (no el modo)?** En kwin, con el
   panel a 120 Hz, haced un ciclo DPMS off→on **sin cambiar de modo**
   (`kscreen-doctor output.DSI-1.dpms.off` → `.on`). 
   - Si **falla igual** (`-110` en `0x9C`), el problema es el re-init del panel bajo
     kwin (carrera disable/enable, backlight, o falta de reset), no el cambio de modo.
   - Si **no falla**, el problema está en el cambio de modo concreto (reconfiguración
     del CRTC/host DSI).

3. **Experimento B — ¿el driver está bien?** Arrancad Sway (o gamescope) como DRM master
   y haced `wlr-randr --output DSI-1 --mode <60Hz>` (o el QAM de Steam).
   - Si **funciona** → el driver de panel y el host DSI están bien; el bug es del camino
     de kwin. Id a R1/R5.
   - Si **falla** → es kernel/host DSI. Id a R2 (0048a/0048b) y revisad el log
     (`dmesg`) del host `msm_dsi_host_power_on/off` y del PHY.

4. **Experimento C — ¿carrera de backlight?** El fix de ROCKNIX #2884 salta la escritura
   de brillo mientras el panel está apagado. Confirmad que vuestro `0028` lo tiene
   (sí, lo tenéis) y, para aislar, probad con `backlight` fijado a un valor constante
   (sin `pocknix-panel-apply` ni demonios de brillo) durante el cambio.

Interpretación más probable con los datos actuales: **el fallo es la secuencia
disable/enable de kwin sobre el host DSI msm**, no el driver del panel. La evidencia
indirecta es que ni armada ni ROCKNIX usan kwin para el panel y ambos rotan modos.
